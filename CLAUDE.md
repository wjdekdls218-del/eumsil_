# 이음실 (Eumsil) — Operating Manual

Mobile-web marketplace + community for trading leftover knitting yarn/tools. Solo project, one developer, no code reviewers. This file is the substitute for a senior engineer looking over your shoulder — read it before touching code, not after something breaks.

**Live**: https://eumsil.vercel.app · **Repo**: github.com/wjdekdls218-del/eumsil_ · **Firebase project**: `eumsil-ab852`

## 0. Orientation (read this first)

- Stack: React 18 + Vite, Firebase (Firestore + Auth), Cloudinary (images), Kakao Maps (location), Vercel (hosting), Firebase Cloud Functions (`functions/`, Node 24).
- No TypeScript, no test suite, no ESLint/Prettier config, no CI. The only safety nets are: this file, `git diff` before you commit, and manually clicking through the app. Act accordingly — be more careful than a linted, tested codebase would require.
- All UI copy is Korean. Do not translate strings, rename Firestore fields, or "clean up" Korean text unless asked. If you must add UI copy, write natural, casual Korean matching the existing tone (반말이 아닌 존댓말, 이음실 특유의 다정한 톤 — see examples like "사진은 필수예요", "저장에 실패했어요. 다시 시도해주세요.").
- Three deploy surfaces move independently. Vercel deploys the frontend automatically on push to `main`. Cloud Functions do **not** auto-deploy — they require `firebase deploy --only functions` run by hand. Firestore security rules also do **not** auto-deploy — they require `firebase deploy --only firestore:rules`. A frontend change, a functions change, and a rules change landing in the same commit does not mean they ship together.
- Security rules live in [firestore.rules](firestore.rules) and are version-controlled, but the **deployed** ruleset is whatever was last pushed with `firebase deploy --only firestore:rules` — the file being correct in git proves nothing about production. Editing rules in the Firebase console silently desyncs them from this file; always change the file and redeploy instead. To read what is actually live, fetch the current ruleset from the `firebaserules.googleapis.com` API rather than assuming it matches.
- The app is served on **two domains off one deployment and one Firebase project**: `eumsil.vercel.app` and `eumsil-portfolio.vercel.app` (portfolio-facing). They share the same Firestore data and the same bundle. Any new domain must be added to Firebase Auth's authorized-domains list or `signInWithPopup` fails there with `auth/unauthorized-domain` — that list is console/API-only config, not in this repo.

## 1. Conventions

### Conventions already in place — follow these exactly
- **Theme tokens, never raw hex in JSX.** User-facing pages import `{ C, FONT }` from [src/theme.js](src/theme.js). Admin pages (`src/pages/admin/**`, `AdminNav.jsx`) import `{ AC, FONT }` from [src/adminTheme.js](src/adminTheme.js). These are two separate palettes (teal `#3DBDB8` vs purple `#6C63FF`) — never mix them or hardcode a color that happens to match one.
- **Mobile shell on every top-level page**: `maxWidth: 430` container, centered with `margin: '0 auto'`, `minHeight: '100dvh'` (or `height: '100dvh'` for flex-column chat-style pages), `background: C.bg`, `fontFamily: FONT`. Copy this shell from an existing page like [src/pages/ProductDetail.jsx](src/pages/ProductDetail.jsx) rather than inventing it.
- **iOS safe-area padding on every fixed bottom/top element**: bottom bars use `paddingBottom: 'calc(Npx + env(safe-area-inset-bottom))'`; side padding on full-width fixed bars uses `max(12px, env(safe-area-inset-left/right))`. See [BottomNav.jsx](src/components/BottomNav.jsx) and [AdminNav.jsx](src/components/AdminNav.jsx).
- **Route guards**: public pages are bare `<Route>`s; logged-in-only pages wrap the element in `<PrivateRoute>`; admin-only pages wrap in `<AdminRoute>`. `PrivateRoute` checks `user === undefined` (loading) vs `null` (logged out) vs truthy (logged in) — never treat `undefined` and `null` as the same state, they mean different things everywhere in this codebase.
- **Firestore doc shape**: `{ id: doc.id, ...doc.data() }` when reading, always paired with `serverTimestamp()` for `createdAt`/`updatedAt` when writing — never `new Date()` client-side for stored timestamps.
- **Modals are bottom sheets**: fixed overlay (`inset: 0`, `rgba(0,0,0,0.45–0.55)`), a `maxWidth: 430` panel pinned to the bottom with `borderRadius: '20px 20px 0 0'`, closed by clicking the overlay backdrop (`onClick` on the outer div, `e.stopPropagation()` on the inner panel). Copy this from `TradeModal`/`TrackingModal` in [ChatRoom.jsx](src/pages/ChatRoom.jsx) or [ReportModal.jsx](src/components/ReportModal.jsx), don't invent a new modal pattern (e.g. `<dialog>`, a portal library).
- **Debug/error logging is tagged**: `console.error('[ComponentName] 실패 설명:', e)` — bracketed component name, Korean description, the error object. Search the codebase for `console.error('[` to see the pattern before adding a new one.
- **Commit messages**: Korean sentence, English Conventional Commit prefix (`feat:`, `fix:`, `perf:`). E.g. `fix: 상품 상세 Timestamp 직렬화 오류 수정 (검은 화면 버그)`. Match this exactly — don't switch to English-only or drop the prefix.
- **Non-obvious business rules get a comment block above the function**, explaining the *why* and the state machine, not the *what* — see the doc-comments on `TradeModal`, `handleTradeConfirm`, `handleTrackingRegister` in ChatRoom.jsx, and the whole of `functions/delivery/scheduler.js`. This is the one place in the codebase where verbose comments are correct — keep doing it for anything touching money, deadlines, or moderation.
- **Cloud Functions folder structure is domain-based** and documented at the top of [functions/index.js](functions/index.js): one folder per domain (`delivery/`, `notifications/`), `utils/firestore.js` for shared `db`/collection refs, `index.js` only wires up exports. Follow the "how to add a function" recipe written there instead of improvising a structure.

### Conventions to add (not consistently followed yet — apply going forward)
- **One source of truth for status strings.** Right now `'완료'`, `'거래완료'`, `'판매중'`, `'예약중'`, `'나눔'` are retyped as literals in at least [Home.jsx](src/pages/Home.jsx), [ProductDetail.jsx](src/pages/ProductDetail.jsx), and [ChatRoom.jsx](src/pages/ChatRoom.jsx), and they've already drifted (see §2, "Status-string drift"). New code should import status constants from a single `src/constants/status.js` instead of retyping the Korean literal. If that file doesn't exist yet, create it the first time you touch status logic rather than adding a fourth copy.
- **One shared Firestore Timestamp normalizer.** The `toDate ? toDate() : seconds ? new Date(seconds*1000) : null` dance is reimplemented separately in ProductDetail.jsx, ChatRoom.jsx (twice), and elsewhere. Extract to `src/utils/firestoreDate.js` (e.g. `toDate(ts)`) the first time you need it in new code, and prefer importing it over pasting the ternary again.
- **Denormalized-field writes are listed, not implied.** Whenever you add a Firestore write that has a "shadow" field elsewhere (e.g. adding a chat message also requires updating `chats/{id}.lastMessage` + `lastMessageTime`; changing a post's status requires it in exactly one place, not both `posts/{id}.status` and some cached copy), write a one-line comment naming both writes so the next edit doesn't drop one.
- **New pages get registered in the same commit** as the route in [App.jsx](src/App.jsx) — don't add a page component without wiring its `<Route>`, and don't add a route without picking the right guard (bare / `PrivateRoute` / `AdminRoute`).

## 2. Mistakes a weaker model will make here — named, with the rule that prevents each

| # | Mistake | Why it happens here specifically | Rule that prevents it |
|---|---|---|---|
| 1 | **Timestamp crash ("검은 화면 버그")** — calling `.toDate()` on a value that's actually a plain `{seconds, nanoseconds}` object, or vice versa. | Firestore `Timestamp` objects survive `onSnapshot`/`getDoc`, but the *same* timestamp arrives as a plain serialized object when passed through React Router `navigate(path, { state })` (see ProductDetail's `prefetched` state). One code path gives you a class instance, the other a plain object. This already caused a real production bug (commit `2fc07b6`). | Never call `.toDate()` directly on a timestamp field that might have come from `location.state` or any non-Firestore source. Always normalize first: `typeof ts.toDate === 'function' ? ts.toDate() : ts.seconds ? new Date(ts.seconds * 1000) : null`. Use the shared `toDate()` util (§1) instead of re-deriving this. |
| 2 | **Status-string drift** — checking a status against the wrong literal. | Confirmed live bug: [ChatRoom.jsx:599](src/pages/ChatRoom.jsx) sets `posts/{id}.status = '거래완료'`, but [ProductDetail.jsx:304](src/pages/ProductDetail.jsx) checks `product.status === '완료'` — these never match, so the "거래 완료" disabled button state silently never triggers. Three files each hand-type their own status → color/label map. | Never hand-type a Korean status literal in a conditional or a color/label map. Import from the single status-constants module (§1). If it doesn't exist yet, that's a sign to create it before adding a fourth copy, not a reason to add a fifth. |
| 3 | **Trusting client-side checks as security.** `AdminRoute`, `isOwner` checks, and ban checks all live in React components. [firestore.rules](firestore.rules) now covers these server-side, but the file in git is not proof of what is deployed, and a new write path added in `src/` gets no rule automatically. | A route guard only stops the UI from *rendering* a button; it does nothing to stop a direct Firestore SDK call from the browser console or a modified client. | Never treat a `PrivateRoute`/`AdminRoute`/`isOwner` check as sufficient protection for a write or delete. When adding or changing any write path (delete a post, ban a user, mark a report resolved), open `firestore.rules`, confirm a matching server-side condition exists for the collection, and if it doesn't, add it and tell the user it needs `firebase deploy --only firestore:rules` — a push to `main` will not ship it. |
| 4 | **Business-rule threshold drift between frontend and Cloud Functions.** The 7-day "seller can force-complete" window in [ChatRoom.jsx](src/pages/ChatRoom.jsx) (`canComplete`) and the 14-day "auto-complete" window in [functions/delivery/scheduler.js](functions/delivery/scheduler.js) are two independently hand-typed numbers describing one business rule. | These live in different languages (JS frontend, Node backend) in different folders, so there's no shared constant to import — a naive edit changes one and misses the other. | When changing any deadline, threshold, or day-count tied to delivery/trade status (currently: 48h tracking deadline, 7-day seller-complete, 14-day auto-complete, 24h/48h notification windows), grep the whole repo (`grep -rn "7 \* \|14 \|48 \* \|24 \*"` style search, or just search the number) for the same magic number elsewhere before assuming a single-file edit is complete. |
| 5 | **Cloudinary/Kakao keys treated as secrets that need hiding.** A weaker model, seeing hardcoded strings like `dw4hwiskc`, `ai5j2gjk`, or the Firebase `apiKey` in [firebase.js](src/firebase.js), will "fix" this by moving them into `.env` and adding error handling for "missing env var," or refuse to write code that includes them. | Firebase web config and an unsigned Cloudinary upload preset are meant to be public — they're restricted by Firebase/Cloudinary console-side rules, not by secrecy. `.env` already exists and holds the *same* values (`VITE_CLOUDINARY_CLOUD_NAME`, `VITE_CLOUDINARY_UPLOAD_PRESET`) but the actual upload code in Write.jsx/ReportModal.jsx doesn't read from it — it hardcodes the string instead, inconsistently. | Don't invent new secret-handling machinery for these two values. If touching upload code, prefer reading `import.meta.env.VITE_CLOUDINARY_*` (since `.env` already defines them) over hardcoding a third copy of the string — but don't treat their exposure in the bundle as a vulnerability to "fix" with hiding.
| 6 | **Leftover verbose `console.log` debugging shipped to production.** [Home.jsx](src/pages/Home.jsx)'s popup-notice logic has ~5 `console.log('[팝업] ...')` lines that were left in after debugging and are now live on `eumsil.vercel.app`. | Nothing catches this — no lint rule, no reviewer. It's easy to add a debug log while chasing a bug and forget to remove it once the fix lands. | Before finishing any task, grep your own diff for `console.log` (not `console.error`) and remove any that were added for debugging rather than for the `[ComponentName] 실패:` error-tag convention (§1). Don't leave "temporary" logs in a commit. |
| 7 | **Committing `dist/` or other build output.** Happened before (commit `b6c2395`) and broke Vercel builds by skipping the actual build step. | Firebase/Vite projects sometimes get built locally before `.gitignore` is set up correctly, and a rebuild silently re-adds tracked files if `dist/` was ever committed once. | Before committing, run `git status` and confirm nothing under `dist/`, `node_modules/`, or `functions/node_modules/` is staged. `.gitignore` already excludes these — if you see them in `git status` anyway, they're likely already tracked from before; investigate rather than force-adding. |
| 8 | **Assuming a new Firestore query with 2+ `where`/`orderBy` clauses just works.** Firestore throws a runtime "requires an index" error the first time a compound query actually executes — it is not caught by anything static. | [NotificationsContext.jsx](src/context/NotificationsContext.jsx) has a comment explicitly documenting this: it deliberately filters only by `uid` server-side and does `isRead` filtering client-side specifically *to avoid* needing a composite index. | When adding a Firestore query with more than one `where()`, or a `where()` combined with `orderBy()` on a different field, either (a) filter client-side for the second condition like NotificationsContext does, matching the existing pattern, or (b) explicitly tell the user a composite index needs to be created in the Firebase console before the feature will work in production — don't silently ship a query that will throw on first real use. |
| 9 | **"Fixing" the lack of tests/lint/TypeScript by introducing one unasked.** Adding Jest, ESLint, or converting a file to `.tsx` is a large, repo-wide-implication change in a project that has deliberately (or at least consistently) run without them for its entire history. | None of these tools exist anywhere in the repo; there's no partial adoption to build on. | Don't add a test framework, linter config, or TypeScript to any file unless the user explicitly asks for it. If test coverage or type safety seems genuinely needed for a specific risky change, say so and ask — don't just start installing devDependencies. |

## 3. Quality bar per deliverable (checkable, not vibes)

**New page/screen** — done means:
- [ ] Route added to [App.jsx](src/App.jsx) with the correct guard (bare / `PrivateRoute` / `AdminRoute`)
- [ ] Uses `C`/`FONT` from `theme.js` (or `AC`/`FONT` from `adminTheme.js` if under `/admin`) — zero raw hex colors in the new file
- [ ] Outer container has `maxWidth: 430`, centered, correct `minHeight`/`height: '100dvh'`
- [ ] Any fixed top/bottom bar has `env(safe-area-inset-*)` padding
- [ ] Loading state and empty/not-found state both render something (never a blank white screen while `loading === true` or data is `null`)
- [ ] Any Firestore write includes `serverTimestamp()` for its timestamp field(s) and updates every denormalized shadow field (§1)
- [ ] No hardcoded Korean status literal — imports from the shared status constants if the page displays status
- [ ] Manually clicked through in the browser at 430px width (or narrower), not just built successfully

**Firestore schema/query change** — done means:
- [ ] Any query with 2+ conditions either matches the client-side-filter pattern or is flagged to the user as needing a console-side composite index (Mistake #8)
- [ ] Any new write path that a non-owner/non-admin/banned user shouldn't be able to trigger is flagged to the user as needing a matching Firestore security rule (Mistake #3) — this codebase cannot verify that for you
- [ ] Any field read that might be a Timestamp uses the shared normalizer, not a fresh `.toDate()` call (Mistake #1)
- [ ] Field names match existing casing/naming exactly (`displayName` not `nickname` on `users/{uid}` — see the HANDOVER.md field glossary) — don't introduce a synonym field for something that already has a name

**Cloud Functions change** — done means:
- [ ] New function is exported from `functions/index.js` per the recipe documented there, in the right domain folder
- [ ] Any magic number shared with frontend logic (deadlines, day-counts) is grepped for and updated in both places, or the user is told which frontend file also encodes the same rule (Mistake #4)
- [ ] User is explicitly told this requires `firebase deploy --only functions` — it will not ship via the Vercel git-push auto-deploy
- [ ] Cost implications considered: scheduled functions run daily and query with `.where()` — confirm the query is bounded (not a full collection scan) before adding

**Bug fix** — done means:
- [ ] Root cause identified and stated in one sentence before the fix (not just "it works now")
- [ ] Checked whether the same bug pattern exists elsewhere (Mistakes #1, #2, #4 are exactly this kind of repeated-copy bug) — if it does, either fix all instances or explicitly tell the user which ones you left
- [ ] Commit message follows the Korean-sentence + English-prefix convention, describing the bug, not the code change

**Any commit** — done means:
- [ ] `git status` shows nothing unexpected staged (no `dist/`, no accidental `node_modules/`)
- [ ] `git diff` reviewed for stray `console.log` debug lines before committing (Mistake #6)
- [ ] Commit message: Korean sentence + `feat:`/`fix:`/`perf:` prefix, matching existing log style

## 4. What to do when uncertain — exact escalation rules

Don't guess-and-ship on any of these; stop and ask the specific question, don't ask a vague "does this look right?":

1. **Firestore security implications** (Mistake #3): if a change adds or changes who can write/delete/read something, read the matching `match /<collection>/...` block in [firestore.rules](firestore.rules) first. If it doesn't already restrict the operation to the right condition, add it and tell the user it needs a separate `firebase deploy --only firestore:rules`. Don't assume rules match the UI guard, and don't assume the deployed ruleset matches the file.
2. **A magic number that looks like a business rule** (48h, 7 days, 14 days, or a new one you're adding): ask whether the same number needs to change anywhere else before treating a single-file edit as complete (Mistake #4). Search first, ask if the search is inconclusive.
3. **Korean copy wording**: if a new user-facing string is needed and isn't a trivial reuse of existing phrasing, don't invent tone — draft it, but explicitly flag it as a draft needing the user's wording pass, rather than presenting invented copy as final.
4. **Firestore field naming**: if you're about to add a field to `users`, `posts`, `chats`, `notifications`, or `community` that might already be covered by an existing field (e.g. almost added `nickname` when `displayName` already exists — this exact mistake happened once, see HANDOVER.md), check the field glossary in HANDOVER.md first; if still unsure, ask rather than adding a near-duplicate field.
5. **Anything touching money, bans, or moderation** (price, ban duration, report resolution, admin actions): implement the happy path, but explicitly call out edge cases you're *not* handling (e.g. "what if the seller is also banned mid-transaction?") rather than silently picking a behavior.
6. **Deploy sequencing**: if a change touches both `src/` and `functions/`, or touches `vercel.json`/`firebase.json`, state explicitly what needs manual action (`firebase deploy --only functions`) versus what ships automatically (Vercel on push to `main`) — don't assume "committed" means "deployed."
7. **Anything that would add a dependency** (a UI library, a state manager, a test framework, TypeScript): ask first. This project has stayed deliberately minimal (4 runtime deps) for its whole history; adding one is a bigger decision here than in a typical repo (Mistake #9).

If none of the above apply and the ambiguity is purely cosmetic (spacing, color shade, icon choice) — use best judgment matching the nearest existing example, no need to ask.
